A file crosses the room as light.

QRelay sends a file from one phone to another using nothing but a screen and a camera. No Wi‑Fi, no Bluetooth, no server, no account. The sender encrypts the file and plays it as a stream of QR codes; the receiver films the screen and rebuilds it. This is everything under the hood, in the order you would explain it.

01

The idea, in ninety seconds

Start here. If the audience only remembers one slide, make it this one.

Every way two phones normally exchange a file goes through something in the middle: a Wi‑Fi router, a cell tower, a Bluetooth pairing, a cloud drive. Each middle party is a place the file can be logged, blocked, or intercepted, and each one needs setup: a password, a pairing dialog, an account.

A screen and a camera are already a communication channel. A screen is a transmitter of about two million pixels; a camera is a receiver that reads them thirty times a second. It is line-of-sight, it is one-directional, and you can see it working with your own eyes. Nobody can join it from the next room.

QRelay treats that as a real network link and builds a protocol on top of it, the way you would over radio: encrypt the payload, cut it into numbered blocks, transmit them as fast as the channel allows, and make the transfer survive the fact that the camera will miss frames.

Say it like this

"Everything on your phone that sends a file needs a network. This needs a window. The screen is the radio, the camera is the antenna, and the QR codes are the modulation."

02

What React Native actually is

The question you will definitely be asked. The short answer: it is not a website in a wrapper, and it is not a compiler to Swift.

An ordinary iOS app is Swift compiled to machine code. An ordinary Android app is Kotlin compiled to bytecode for the Android runtime. React Native is a third path: you write JavaScript, and it drives the real native UI toolkit.

The distinction that matters: a button in QRelay is not an HTML <button> and not a picture of a button. It is a genuine UIView on iOS and a genuine android.view.View on Android, created and positioned by native code, taking touches from the real touch system. JavaScript decides what should exist; the platform decides how to draw it.

That is the difference from a hybrid framework like Cordova or a plain web app, where the entire interface is a web page inside a browser view. It is also the difference from Flutter, which brings its own rendering engine and paints every pixel itself. React Native borrows the platform's own widgets.

ApproachWhat runs your logicWhat draws the pixelsExample
NativeCompiled Swift / KotlinPlatform UI toolkitInstagram's original apps
Web wrapperJavaScript in a browser viewThe browser engineCordova, Ionic
FlutterCompiled DartIts own engine (Impeller/Skia)Google Pay
React Native this appJavaScript on HermesPlatform UI toolkitQRelay, Discord, Shopify

QRelay was originally written in Flutter and rewritten in React Native. The reason was practical rather than technical: building a Flutter app for an iPhone requires a Mac, and Expo lets an iPhone run the app straight from a Windows PC. The protocol survived the move unchanged, which is itself a point worth making: the interesting part of this project is not the framework.

And what is Expo?

React Native gives you the bridge to native UI, but not a camera, not a file picker, not haptics. Expo is the layer above: a curated set of native modules with one consistent JavaScript API, plus the tooling to build and ship without touching Xcode or Android Studio.

Two pieces of Expo matter for the demo:

  • Expo Go — a free app on the App Store that is, in effect, a pre-built React Native host containing every Expo native module. It downloads your JavaScript bundle and runs it. That is why an iPhone can run this app with no Mac, no Apple developer account and no code signing: the signed native shell is Expo's, and only the JavaScript is yours.
  • EAS Build — when you need native code Expo Go does not carry, or a real home-screen icon, Expo compiles the app on their machines (including Macs) and hands back an installable binary.
The tradeoff, stated honestly: Expo Go can only run native modules it already contains. Three of QRelay's six edit operations (PDF↔Word conversion and OCR) need engines Expo Go does not ship, so the app detects that and greys those tiles out with a reason rather than failing when tapped.
03

How the phone actually runs it

From tapping the icon to pixels on glass. This is the part that separates a demo from an explanation.

The JavaScript engine

Your code does not run in Safari or Chrome. It runs on Hermes, a JavaScript engine Meta wrote specifically for mobile. Its defining choice: instead of parsing JavaScript source at launch, Hermes compiles your code ahead of time into compact bytecode, and the app ships that bytecode.

You can see it in this project. npx expo export produces a single .hbc file — Hermes bytecode — of about 5 MB, holding all 2,020 modules of app code plus every library. At launch the engine memory-maps that file and starts executing almost immediately, with no parse step. That is why a React Native app can cold-start in well under a second despite being "a JavaScript app".

Three threads, and why it matters here

A React Native app runs on several threads at once. Three of them decide whether QRelay feels smooth or terrible:

The New Architecture

Older React Native sent every instruction between JavaScript and native as a serialised JSON message over an asynchronous "bridge". It worked, but it was a bottleneck and it made anything synchronous impossible.

React Native 0.76 made the New Architecture the default, and this project runs 0.86. JavaScript now holds direct references to native objects through JSI (the JavaScript Interface), so calling a native module is a direct function call rather than a serialised round trip. The renderer, Fabric, builds the view tree in C++ shared across platforms.

For QRelay this is not a footnote. The camera passes decoded QR strings to JavaScript many times per second, and the stream screen replaces an SVG path ten times per second. On the old bridge, both of those would be queued serialisations.

If someone asks "isn't JavaScript slow?"

"For this app the bottleneck is physics, not the language. The camera can only read about ten QR codes a second. Our decoder handles a frame in well under a millisecond, so we spend 99% of every frame waiting for light. The one place JavaScript was genuinely too slow — hashing a multi-megabyte file — we handed to the operating system."

The stack, layer by layer

Fifty-three TypeScript files in five layers. The rule that shaped all of it: the protocol must not know it is in a phone app.

src/coreThe protocol. base45, CRC-32, deflate packing, the block selector, the fountain encoder and decoder, AES-GCM, QR matrix generation, and the sender and receiver state machines. Zero React and zero Expo imports. These same files run inside the app and inside the test runner on a PC, unmodified.
src/stateFour Zustand stores. settings and history persist to the phone's key-value store; send and receive hold the live transfer. Zustand was chosen over Redux because a store is a plain function and no provider has to wrap the tree.
src/filesThe world outside. Picking a file, saving one, sharing, opening in another app. All the platform differences live here — Android gets a real "open with" intent, iOS routes through the share sheet.
src/uiThe design system. Colour tokens for both themes, two type scales, one spring shared by every control, the icon set, and twelve components. No component in src/app writes a raw colour or font size.
src/appThe screens. Ten files, and the folder structure is the navigation: send/key.tsx is the route /send/key. This is Expo Router's file-based routing, the same idea as Next.js.
Why the separation earns its keep: the fountain codec has 36 tests that run in about a second on a laptop, with no phone, no emulator and no camera. A protocol bug is found in a unit test, not by squinting at two phones. It also meant the entire Flutter-to-React-Native rewrite was a port of the UI layer; the protocol was translated line for line and its tests came with it.

05

The protocol

What a file goes through between "Send" and light leaving the screen. Six stages, each with a reason.

Stage 1 — Pack

The file is deflated at level 6, in 128 KB chunks that yield to the event loop between them so the screen keeps animating. The result is kept only if it saves at least 3% of the bytes; a flag in the key frame records whether it was used.

Text, CSV, JSON and Office documents shrink dramatically. JPEGs, ZIPs and most PDFs do not, because their contents are already compressed — so the packer gives up after a megabyte if it has saved under 1%, and the file streams as-is. Since the channel is the bottleneck, every byte removed here is time saved directly.

Stage 2 — Seal

A 256-bit key and 96-bit nonce come from the operating system's cryptographic random generator. The packed bytes are encrypted with AES-256-GCM, which appends a 16-byte authentication tag. Separately, SHA-256 is taken over the original file, so the receiver can prove it rebuilt the exact bytes that were picked, not merely something that decrypted cleanly.

Stage 3 — Frame

Two frame types go on the wire. Everything the receiver needs once is in the key frame; everything repeated lives in the data frames, where every byte costs time.

Seventeen bytes of overhead on a 500-byte payload: 3.3%. Each field earns its place.

  • session — four random bytes identifying this transfer. If two people stream in the same room, the receiver ignores frames that are not its sender's, and says so on screen.
  • seed — the whole trick. This number alone tells the receiver which blocks the payload combines, so the sender never has to list them.
  • crc-32 — QR has its own Reed–Solomon correction, so a bad decode is rare, but it is catastrophic here: one corrupt payload poisons every block it touches in the linear system. The CRC is the seatbelt.
06

Fountain codes: the heart of it

The single most interesting piece of engineering in this project, and the one that will get questions.

Set up the problem first, because the solution only impresses if the audience feels the difficulty.

The file is 48 blocks. The sender shows them in order. The camera, being a camera pointed at a moving screen by a human hand, misses blocks 7, 22 and 40. Now what? Over Wi‑Fi, the receiver says "resend 7, 22 and 40". Here it has no voice. The screen cannot hear it.

The naive fix is to loop: show all 48 again, and again, until the receiver has them all. That works, and it is terrible. With 15% of frames missed, you need many full passes, because each pass is likely to miss a different block, and the coupon-collector maths is brutal.

The line that makes it click

"Think of a fountain. You do not ask a fountain for a specific droplet. You hold up a cup, and when the cup is full, you have water. It does not matter which droplets you caught."

How a repair frame is built

After the in-order pass, the sender starts emitting repair frames. A repair frame is the XOR of a random half of the blocks — block 3 XOR block 9 XOR block 17 XOR block 31, and so on. Which half is chosen by a seeded random number generator, and the seed is written in the frame header.

So the receiver, reading only the seed, runs the identical generator and knows exactly which blocks went into that payload, without the sender spending a single byte listing them. That is why the same deterministic generator lives in both the encoder and the decoder, and why it is hand-written rather than using Math.random: the sequence must be identical to the bit on both phones forever.

// Both sides derive the same block set from the seed alone
maskFor(seed) {
  if (seed % cycle < K) // in-order pass: just block q
    return bit(seed % cycle);
  const rng = new FrameRng(mix(seed));   // deterministic, 32-bit
  for (w = 0; w < words; w++)
    mask[w] = rng.nextWord();            // each block in with p = ½
  return mask;
}

Solving it: linear algebra over one bit

Here is the reframe that makes the whole thing tractable. Every frame is an equation. The unknowns are the blocks. XOR is addition in a number system with only two values, 0 and 1 — mathematicians call it GF(2), the field of two elements.

A frame carrying block 3 alone says b₃ = (those bytes). A repair frame says b₃ ⊕ b₉ ⊕ b₁₇ = (those bytes). Collect enough independent equations and you can solve for every unknown. This is Gaussian elimination, the same procedure as solving simultaneous equations in school, except addition and subtraction are both just XOR, which is why it is so fast.

Why it is incremental, not batch

A textbook implementation would collect all the frames and then solve. That would mean a frozen screen for a second at the end and no progress to show along the way. Instead the decoder keeps rows in echelon form as they arrive, indexed by their lowest set bit:

  1. A frame arrives. XOR out every block already known, clearing those bits.
  2. Reduce what remains against the stored pivot rows.
  3. If one bit is left, that block is solved — and the solution is pushed back through every stored row, which often cascades into solving several more.
  4. Otherwise store it as a new pivot row.
  5. Once there is a pivot for every remaining unknown, one back-substitution pass finishes the file.

This is why the block grid on the receiver's screen fills left to right during the in-order pass, stalls at the gaps, then jumps to complete all at once. That visual is not a designed flourish — it is literally the algorithm reaching full rank. The progress display shows blocks rather than a percentage bar for exactly that reason: a linear bar would be a lie.

The cycle, and the number 0.35

The stream runs in cycles of K + ⌈0.35 K⌉ frames: the in-order pass, then repair frames worth 35% of the file, then the pass again for anyone who arrived late. For a 48-block file that is 48 + 17 = 65 frames per cycle.

A receiver that missed u blocks needs about u + 2 repair frames to recover, whichever blocks they were — dense repair frames are near-optimal for this. 35% therefore covers loss up to roughly a quarter of frames within a single cycle, which is well beyond what a steady hand produces. Past that, a second cycle finishes the job.

This design replaced a textbook one. The first implementation used the classic Luby Transform scheme: a robust soliton degree distribution with a peeling decoder. Measured, it needed about 1.4× the theoretical minimum number of frames. The reason is specific — after a systematic first pass, a degree-2 repair frame only helps if both its blocks are missing, which is rare. Dense frames plus real elimination now finish a 200 KB transfer at 15% loss within 6% of the information-theoretic floor. The tests assert that bound, so it cannot silently regress.
07

Cryptography and the threat model

Be precise about what this protects against and what it does not. Overclaiming security is the fastest way to lose a technical audience.

What happens

  1. The OS cryptographic generator produces a 256-bit key and a 96-bit nonce, fresh for every transfer.
  2. The packed file is encrypted with AES-256-GCM, an authenticated cipher: it provides confidentiality and tamper detection, appending a 16-byte tag.
  3. SHA-256 is computed over the original file, and travels in the key frame.
  4. The receiver decrypts, checks the GCM tag, inflates if flagged, then checks the SHA-256. Any failure means nothing is saved and the screen says why.

What it defends against

  • Someone who walks in after the key QR has gone. They see only ciphertext — no file name, no size, no way to test a guess.
  • A recording of the stream, played back later. Same result: without the key it is noise.
  • Corruption in transit. The GCM tag and the SHA-256 both have to match.
  • Data at rest leaving the phone. Nothing is uploaded, no account exists, the session key is held in memory and dropped when the flow ends.

What it does not defend against

  • A second camera during those three seconds. If someone films the key QR, they can decrypt everything. The security model is literally "who can see the screen right now".
  • Proving who the receiver is. The sender cannot tell which phone scanned the key.
  • A compromised phone. If the OS is owned, so is the file.
Answer to "is that secure enough?"

"The trust model is line of sight, and it's deliberate. You can see who is in the room and who is holding a phone up. That's a weaker guarantee than a signed certificate chain, but it's one a human can actually verify — which is more than most people can say about the apps they send documents through."

The upgrade path, if asked

Authenticating the receiver is a known extension and does not change the stream format at all. The receiver would display its own public key as a QR first; the sender scans it and wraps the session key with X25519 for that receiver alone. Two scans instead of one, and everything after is identical. Worth mentioning because it shows the design has room.

08

Getting bytes into a QR code

There is a real optimisation here, and a genuine bug that was caught while preparing this document.

Why base45 and not base64

QR codes have four encoding modes. Two matter: byte mode stores 8 bits per character, and alphanumeric mode packs two characters into 11 bits — 5.5 bits each — but only from a restricted 45-character set: digits, uppercase letters, space, and eight symbols.

Binary data has to be turned into text to use alphanumeric mode. base64 needs characters outside that set, forcing byte mode. base45 (RFC 9285) was designed for exactly this: its alphabet is the QR alphanumeric set, and it packs two bytes into three characters.

EncodingQR modeBits per 2 bytesOverhead
Raw binarybyte16.00% (theoretical)
base45 usedalphanumeric16.53%
base64byte21.333%

Raw binary looks free but is not usable: the iOS and Android scanner APIs differ in how they hand back non-text payloads, while both return alphanumeric text identically. base45 costs 3% and works the same everywhere — the right trade for a protocol that must be byte-identical across platforms.

The bug found while writing this brief

The QR library, left to its own devices, picks the smallest symbol that fits. It also spots runs of digits and packs those into numeric mode, which is denser still. Both are sensible defaults. Together they caused a serious defect.

Every frame carries different ciphertext, so the digits fall differently each time. Measured across 200 consecutive frames at the Balanced preset, the symbol landed on version 14, 15 or 18 depending on the frame — a 73-module code, an 77-module code and an 89-module code, all drawn into the same square on screen. The module pitch changed on every single frame, forcing the receiver's camera to re-lock scale ten times a second.

The fix is one argument: pin the version per preset, so the symbol is always 89 modules at Balanced. A regression test now renders 60 frames at each preset and asserts exactly one size comes out.

// Before: the encoder chose. Frames wandered v14 → v18.
QRCode.create(text, { errorCorrectionLevel: 'M' })

// After: pinned per preset. Every frame is identical in size.
QRCode.create(text, { errorCorrectionLevel: 'M', version })
This is a great story to tell

"The unit tests all passed. The code was correct in the sense that every frame decoded. It was only wrong as a physical transmission — the picture kept changing size, and a camera has to refocus when that happens. That's the class of bug you only find by thinking about what the hardware on the other end is doing."

Error correction level

QR codes carry Reed–Solomon correction at one of four levels. QRelay uses M, which tolerates about 15% damage and spends about 15% of the symbol on redundancy. Level L would fit more data per frame but breaks up under glare and motion blur; level Q or H would survive a coffee stain, which is not the failure mode when the "paper" is a glowing screen 20 cm away. M is the right point for a clean, close, well-lit target.

09

Rendering and motion

Ten QR frames a second, every one freshly computed, while the rest of the interface stays at 60.

Drawing a QR without images

The obvious approach — render each frame to a PNG and swap an image — means encoding a bitmap ten times a second and pushing it across to native. Instead the module grid is converted into a single SVG path: runs of adjacent dark modules on a row merge into one rectangle, so an 89-module frame becomes a few hundred sub-paths instead of several thousand separate squares.

One detail worth mentioning because it is the kind of thing that only shows up on a real screen: each row's rectangle is drawn 1.03 modules tall rather than exactly 1. Anti-aliasing between two rows that touch exactly can leave a hairline of background colour, and a hairline through a QR code is damage the decoder has to correct. A 3% overlap removes it.

Building frames before they are needed

Composing a frame — XOR the blocks, base45 it, run the QR encoder, build the path — takes a few milliseconds. At 10 fps there is a 100 ms budget, so it fits, but doing it exactly when the frame is due means a visible stutter whenever the work lands badly.

A small cache builds ahead instead: forty frames deep, one per turn of the event loop, so each piece of work is a few milliseconds and never a long block. Frames behind the playhead are dropped. If the stream ever outruns the builder the screen counts the stalls and shows them, rather than pretending.

Animations that cannot stutter

Every animation in the app runs through Reanimated, which compiles animation callbacks into "worklets" that execute on the UI thread rather than in JavaScript. The practical consequence: while the JavaScript thread is busy XOR-ing a 2,000-block file, the countdown ring still drains smoothly and the button still springs under a finger, because those animations are not waiting on JavaScript at all.

One spring is shared by everything: mass 1, stiffness 420, damping 22 — about 340 ms to settle with one small overshoot. Controls give 4% under a finger in 80 ms and spring back on release. Using a single physical model everywhere is what makes an interface feel like one object rather than a pile of components.

A transfer, moment by moment

Narrate this over a live demo, or use it as the backbone of the talk. Times are for a 23 KB PDF at the Balanced preset.

  1. t = 0

    Pick

    The system file picker returns a handle. The app checks the size before reading any bytes — a 30 MB video is rejected on the spot rather than after loading it into memory.

  2. + 0.2 s

    Estimate

    The Send screen shows 48 blocks and "about 8 s". The estimate is real arithmetic — block count ÷ frame rate, plus the key hold and 5% repair allowance — not a guess. Changing preset re-counts it immediately.

  3. + 0.3 s

    Pack, hash, seal

    Deflate runs in chunks (this PDF does not shrink, so it is skipped). The OS hashes the file. AES-256-GCM encrypts. Progress labels name the actual step, because on a large file this is several seconds and a spinner with no noun is useless.

  4. + 0.5 s

    Two confirmations

    "Receiver has the camera open" and "screens 20–30 cm apart". Not bureaucracy — a stream started before the other phone is ready wastes the entire key window, which is the one non-recoverable part of the protocol.

  5. + 1 s

    Key amber

    Brightness goes to 100% and sleep is blocked. The key QR appears inside a ring that drains over three seconds. The receiver's reticle snaps and turns amber: keyLocked. It now knows the file name, size, block count, and what the result must hash to.

  6. + 4 s

    Stream green

    The screen goes black and frames begin at 10 fps. Black stage, white card: maximum contrast, no interface glow near the code. Telemetry shows frame number, pass or repair, and elapsed time.

  7. + 4–12 s

    Receive

    The camera decodes on its own thread and hands strings to JavaScript. Each one is CRC-checked, session-checked, deduplicated by seed, then XOR-ed into the linear system. Blocks pop green as they solve. Updates to the screen are throttled to about 10 per second — the camera fires far more often than a human eye needs.

  8. + 12 s

    Full rank

    The last equations resolve together and the grid completes. Phase goes to verifying; the app yields one frame so that label actually paints before the decrypt work begins.

  9. + 12.3 s

    Verify and save

    Decrypt, check the GCM tag, inflate if flagged, check SHA-256 against the value from the key frame. Only then is anything written to disk. The checkmark draws itself. A failure at any step saves nothing and explains which step failed.

How it is verified

Worth a slide. It is what separates a prototype from engineering.

Limits, and what comes next

Name your own limitations before the audience does. It reads as confidence, not weakness.

Honest limits today

  • Speed. About 5 KB/s. This is a physics ceiling, not a coding one: the camera reads ten frames a second and each holds 500 bytes.
  • 20 MB cap. Above that the wait is unreasonable.
  • Two phones, held still. Not a background transfer. You are committed for the duration.
  • Three of six edit operations need a native build Expo Go cannot provide, and say so rather than failing.
  • The presets are theoretical. They were computed, not measured on real hardware. The first real session tunes them from the on-screen decode rate.

Where it goes

  • Measure and re-tune the presets from the live decode counter.
  • Authenticate the receiver with X25519, two scans, stream format unchanged.
  • Colour QR — three data layers in one symbol using red, green and blue channels, potentially tripling throughput. The decoder maths already supports any block source.
  • A development build to unlock OCR and document conversion.
  • A live camera-rate readout so the app picks its own preset by watching how fast the receiver is actually decoding.
Closing line

"It is not going to replace AirDrop. What it shows is that if you treat a screen as a transmitter and take the engineering seriously — coding theory, real cryptography, honest interface design — two devices that share nothing but a line of sight can still move a file, verifiably and privately."

Questions you will get

Tap to open. Answers are short on purpose — say the first sentence, and expand only if they push.

Why not just use Bluetooth or AirDrop?

They are faster, and for everyday use you should. This solves a different problem: transfer when there is no shared network, when radios are off or blocked, or across a boundary where you do not want a pairing record at all — between an air-gapped machine and a phone, for example. And it is verifiable by eye: you can see exactly where the data is going.

Is JavaScript not too slow for cryptography?

For AES-256-GCM at these sizes, no — the library is an audited constant-time implementation and encryption of a 1 MB file takes a fraction of the time the stream itself needs. But two things were too slow or impossible in JavaScript and were moved to the OS: hashing a large file with SHA-256, and generating cryptographic randomness, which Hermes cannot do at all because it has no crypto global.

What happens if the camera misses frames?

Nothing special — that is the normal case the protocol is built for. The sender keeps emitting repair frames, each an XOR of a random half of the blocks. Any sufficiently large set of frames reconstructs the file, so missing specific ones does not matter. Measured, a 200 KB transfer with 15% of frames dropped finishes within 6% of the theoretical minimum number of frames.

Could someone steal the file by filming the screen?

Only if they filmed the first three seconds. The stream is AES-256-GCM ciphertext; the key exists in one QR code, shown once. Someone who arrives after that gets random-looking bytes with no file name and no size. Someone who was there for the key, camera up, can decrypt it — and that is the deliberate trust model: whoever can see the screen at that moment is who you are sending to.

Why did you rewrite it from Flutter?

A practical constraint. Building a Flutter app for an iPhone requires a Mac, and I develop on Windows. Expo Go runs a React Native app on an iPhone straight from a Windows PC with no signing and no Apple account.

The rewrite is itself the argument for how the code is organised: the protocol layer was translated almost line for line, its tests came with it, and only the interface was genuinely rebuilt. When the framework is replaceable, the framework was not the interesting part.

Why write your own fountain code instead of using a library?

The first version was the textbook algorithm — Luby Transform with a robust soliton distribution and a peeling decoder. Measured, it needed about 1.4× the minimum number of frames, because after an in-order first pass the low-degree repair frames a soliton distribution produces are usually redundant. Dense frames plus real Gaussian elimination brought that to within 6%. The lesson: the standard algorithm was designed for a case that is not quite this one.

How do the two phones stay in sync without talking?

They do not need to. Every frame carries a seed, and both sides run an identical deterministic random number generator over it, so the receiver derives exactly which blocks a payload combines from that one number. The generator is hand-written rather than the language's built-in one precisely because the sequence has to be identical on both phones forever.

What if two people stream in the same room?

Each transfer has a random four-byte session id in every frame. The receiver locks to the session in the key it scanned and ignores the rest, and the status line tells you it is doing so.

Why encrypt before compressing, or is it the other way around?

Compress first, then encrypt — and the order is forced. Encryption output is statistically indistinguishable from random noise, and random data does not compress. Doing it the other way would save nothing. The app also only keeps the compressed version if it saves at least 3%, so a JPEG or a ZIP streams as-is instead of paying for a pointless inflate on the other end.

How big can a file be?

Hard cap 20 MB, warning above 1 MB. At 5 KB/s, 20 MB would take over an hour of holding two phones still. The limit is a UX decision rather than a technical one — the protocol itself handles up to 65,535 blocks.

Does it work in the dark? Through glass? On a cracked screen?

Dark is fine, the screen is the light source and the app forces brightness to maximum. Glass is fine unless it reflects — glare is the real enemy, which is why the Reliable preset exists with fewer, larger modules. A cracked screen degrades gracefully: QR's Reed–Solomon correction absorbs roughly 15% damage per frame, and anything it cannot fix is just another dropped frame the fountain layer already handles.

What was the hardest bug?

A frozen button with no error. Generating the session key called crypto.getRandomValues, which exists in every browser and in Node but not in Hermes, so it threw. The error should have surfaced as a toast — but the toast animation had a second bug where two assignments to the same animated value cancelled each other, so nothing appeared. Two unrelated bugs producing one silent symptom.

The most interesting bug is the QR one: frames changing size ten times a second because the encoder was being clever about digit runs. Every test passed. It was only wrong as physics.

Demo runbook

Live demos fail in rooms with projectors and bad lighting. Plan for it.

Before you leave

  1. Open the app on both phones while you still have internet, and leave them open. Expo Go fetches the bundle once; after that the transfer itself needs no network.
  2. Put a small, recognisable file on the sending phone — a one-page PDF around 20–50 KB. Something that finishes in under ten seconds.
  3. Turn Reduce Motion off, or set Animations to "Always on" in the app's settings, so the interface actually moves.
  4. Charge both phones. Full brightness plus camera drains fast.
  5. Set both to Do Not Disturb. A notification banner over the QR is a dropped frame.

In the room

  • Hold 20–30 cm apart and keep both phones roughly still. Brace elbows on a table if you can.
  • Avoid overhead glare. If the ceiling lights reflect off the sender's screen, tilt it rather than moving further away.
  • Start the receiver first. The key QR is the one non-recoverable moment — if the camera is not up, the receiver cannot decrypt anything that follows. That is exactly why the app makes you tick "Receiver has the camera open".
  • If the key is missed, tap "Show the key again" on the stream screen. It does not restart the transfer.
  • If scanning struggles, drop to Reliable in settings. Fewer, larger modules.

If it fails on stage

Have the fallback ready and treat it as part of the talk, not an apology. The plan artifact contains a working browser prototype that streams real QR frames and decodes them with simulated camera misses — that runs on any laptop with no phones at all.

Then say the true thing: "This is a line-of-sight optical channel. Lighting and hand shake are genuine variables, which is why there are three presets and why the whole protocol is built around frames going missing." A failed demo that you can explain the physics of is a better demonstration of understanding than one that just works.

The five-minute version, if you are cut short

  1. The screen is a transmitter, the camera is a receiver. No network in between.
  2. The camera cannot say "resend", so the sender never stops — fountain codes, any sufficient set of frames rebuilds the file.
  3. Every frame is one equation, blocks are the unknowns, XOR is the arithmetic. Solve as they arrive.
  4. Encrypted with AES-256-GCM; the key is one QR shown for three seconds, so only who is in the room can read it.
  5. About 5 KB/s. Slow, verifiable, and it works with every radio turned off.
